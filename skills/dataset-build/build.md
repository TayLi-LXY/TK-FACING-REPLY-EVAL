## description: 指导为AI评测场景构建评测集：形态选型、数据来源、列结构设计、标准答案治理、抽样与质量检查。当用户需要为新AI场景构建评测数据集、设计评测数据结构或治理标准答案时使用。

# 评测集构建

本技能提炼自四个已落地的评测场景实战：客户回复（打分型21维）、话术提示（打分型11维）、任务完成判断（判定型多轮多任务）、任务偏离（判定型多轮单值）。拿到任何新的AI评测场景，按下面七步走。四场景的列结构实录、规模数字和踩坑细节见文末附录。

## 术语表

| 术语       | 定义                                                         |
| ---------- | ------------------------------------------------------------ |
| 评测集     | 结构化数据表（xlsx），一行对应一次被评AI的调用（或调用的一轮） |
| 判定型     | 输出有客观对错（0/1），代码比对标准答案打分                  |
| 打分型     | 输出质量是连续谱，按维度分ABCD档，由打分模型评判             |
| 标准答案   | 判定型评测集中的期望输出列，打分的比对基准                   |
| 序列       | 一段完整多轮对话，多轮场景下拆成多行，共享一个对话序列ID     |
| 拆行形态   | 多轮对话按轮拆行，每行=一轮调用，靠对话历史列携带上下文      |
| 溯源元数据 | 标记数据出处的列：课程/章节/数据来源/源文件名                |
| 防泄漏     | 答案列和元数据列绝不能进入判定/打分调用的输入                |

## 第一步：场景定性（决定评测形态）

核心判断只有一个：**被评AI的输出，有没有客观对错？**

- **有标准答案可对** → 判定型。答案是0/1或离散值，跑批后代码比对打分，准确率可精确计算。例：任务完成判断（每轮输出各任务complete=0/1）、任务偏离（每轮输出偏离=0/1）。

- **质量是连续谱、没有唯一正确输出** → 打分型。设计评测维度，每维ABCD四档，由打分模型按维度PE评判。例：客户回复（21维）、话术提示（11维）。

第二个判断：**被评AI是单轮调用还是多轮状态机？** 多轮（本轮输入依赖上轮输出）就必须用序列+拆行形态，单轮一行一条即可。

四场景对照表：

| 场景         | 形态   | 单轮/多轮 | 判定粒度                 | 答案来源               |
| ------------ | ------ | --------- | ------------------------ | ---------------------- |
| 客户回复     | 打分型 | 单轮      | 21维，每维ABCD档         | 无标准答案，维度PE定档 |
| 话术提示     | 打分型 | 单轮      | 11维，每维ABCD档         | 无标准答案，维度PE定档 |
| 任务完成判断 | 判定型 | 多轮      | 每轮×每任务 complete=0/1 | 业务修订跑批草稿       |
| 任务偏离     | 判定型 | 多轮      | 每轮单值 偏离=0/1        | 生产标注（纯生产版）   |

形态定了，后面每一步的做法都跟着定：判定型的重心在标准答案治理，打分型的重心在输入字段与打分PE的对齐。

## 第二步：数据来源

**生产日志回流为主 + 人工构造边界case补充，70/30双轨原则**：

- 约70%来自真实生产数据回流，保证分布真实——评测集上的准确率才能代表线上效果；

- 约30%人工构造边界case（红线违规、罕见但重要的失败模式、标杆样本），补生产数据里采不到的角落。边界case由业务方自主编写，不用AI生成，避免锚定效应。

**判定型场景的标准答案三种来源，按可信度排序**：

1. **业务标注**——业务方逐行确认过的答案，金标准；

1. **生产系统标记**——生产系统运行时落下的判定结果，可信但需抽检（见常见坑第7条）；

1. **AI构造预设**——AI生成样本时预设的答案，最弱，容易有标注争议。

AI构造行是否保留在最终评测集里，**必须和需求方确认**。我们的实践结论：纯生产版更可信——任务偏离评测集最终剔除了全部AI构造行，只留生产来源。

## 第三步：数据抽取与字段补齐

评测集的原料不是现成的一张表：**对话内容和场景元数据通常分两处存，抽取 = 两者按键关联**。按下面五步操作。

1. ### 定位原始数据源

两类源，缺一不可：

| 源           | 形态                  | 实例                                                         |
| ------------ | --------------------- | ------------------------------------------------------------ |
| 生产对话导出 | 按课程/日期组织的目录 | 陪练数据/20260615-回复/ 下 BAC 前缀文件夹                    |
| 课程元数据表 | xlsx多sheet           | HWP智慧培训--课程和场景数据.xlsx，含"对练场景""对练用户"等sheet |

先确认两边的关联键（我们的场景是场景id），再动手写抽取脚本。

1. ### 字段关联补齐

以场景id为关联键，从课程元数据表补齐评测输入需要的字段。我们的实例：

| 目标字段        | 来源                                   |
| --------------- | -------------------------------------- |
| sceneBackground | "对练场景"sheet 的"场景背景（AI）"列   |
| userProfile     | 按场景id关联"对练用户"sheet 的客户详情 |
| userPersonality | "性格（AI）"列                         |

**纪律：章节/知识点/任务等字段必须严格来自课程表对应场景id的记录，禁止手动填写或跨场景映射。** 手填的字段和课程表对不上账时，没人查得出来错在哪一行。

## 第四步：数据形态与列结构

### 单轮打分型

一行 = 一条待评输出。列分四段：输入列 + 待评输出列 + 维度打分列（每维两列：维度名_分、维度名_理由）+ 溯源元数据列。

两条硬规则：

1. **输入列名必须与打分PE的占位符名一字对齐**（英文键，如 chatScene/sceneBackground/userProfile/chatHistory/taskTitle/taskDesc）。列名和占位符对不上，跑批时字段填错位，打分全废。

1. **输入列必须完整复刻生产agent的真实输入字段**——生产传什么、传几个、哪个是空的，评测集就照搬什么。不能凭想象增删字段：生产不传对话历史就不加对话历史列，生产的 aiTask 始终为空就保留这个空字段。评测即生产，格式简化过的评测集测出来的结论不能外推到线上。

### 多轮判定型（拆行形态）

一行 = 序列内的一轮调用。标准列结构：

| 列                                | 说明                                                        |
| --------------------------------- | ----------------------------------------------------------- |
| 课程 / 章节                       | 溯源元数据，也是序列分组键的一部分                          |
| 对话序列ID                        | 序列唯一标识，**必须带课程-章节前缀**（如 BAC-开启面谈-D1） |
| 知识点                            | 该轮所属知识点                                              |
| 轮次                              | 序列内从1连续递增                                           |
| 对话历史                          | JSON数组字符串，累积到当前轮（含本轮消息）                  |
| 当前消息                          | 本轮被评的那句话，纯文本                                    |
| 任务列表 / 任务要求               | 该轮判定所需的规则上下文                                    |
| 答案列（期望结果/期望判断）+ 理由 | 标准答案，判定跳的输入里绝不出现                            |
| 数据来源                          | 生产 / AI                                                   |

三条硬规则：

1. **对话历史前缀延续**：第N行的对话历史 = 第N-1行的对话历史 + 上一轮问答。历史是累积的，第N轮条目数 ≥ 第N-1轮。

1. **序列分组必须用 章节+序列ID 双键**（或直接把ID加课程-章节前缀）。不同章节的源文件各自从 S01/D1 编号，只按序列ID单键分组会把不同章节的序列混成一个（见常见坑第2条）。

1. **状态接力有约定就写进README**：如任务完成判断的"上一次任务完成情况"列，跑批方须按序列分组、轮次升序执行，每轮把上轮判定输出作为本轮该字段输入，首轮传空。

### 溯源元数据列

无论哪种形态，都带上：课程、章节、数据来源（生产/AI）、源文件名。作用：出问题能回溯到源文件；按来源过滤（如剔除AI行）；按章节统计覆盖。注意这些列只用于管理，绝不进判定/打分输入。

## 第五步：标准答案治理（判定型专属）

答案未经业务确认时，两条路选一条：

- **路线A：小规模业务抽检**——业务方从答案里抽一部分逐行核对，估计答案错误率，可接受则放行；

- **路线B：先跑一轮判定 + 业务修订分歧行**——答案列先留空或用现有标记，跑一轮判定agent，把判定结果与现有答案的分歧行（或跑批草稿全量）交业务修订成标准答案。任务完成判断走的就是这条路：期望结果列交付时留空，客户跑批后业务修订。

不管走哪条路，**深钻分析环节必须留"疑似答案错误"出口**：模型判定与标准答案不一致时，允许深钻结论是"答案可能标错了"而不是强行给模型找错。没有这个出口，错答案会被当成真理迁就，优化方向跟着跑偏。

配套动作：

- [ ] 答案为空/非法值（如0/1题出现其他值）的行单独列清单，交需求方决定剔除还是补标，不要悄悄处理

- [ ] 判定PE与打分PE物理分离（两跳调用）：判定跳的输入不含答案，打分跳才注入答案比对——指令级"请忽略答案列"不算隔离

## 第六步：抽样与覆盖检查

规模经验值（按需求和预算调整）：

| 用途             | 经验值                                             |
| ---------------- | -------------------------------------------------- |
| 每场景快速验证集 | 30条                                               |
| 每章节正式评测集 | 50-100条                                           |
| 全量回流大表     | 不抽样，全量保留（判定型两万行级别跑批成本可接受） |

覆盖检查三项：

- [ ] **正负样本占比**：判定型看0/1分布（如任务偏离全量20990行中偏离样本占23.4%），全正或全负的评测集测不出东西；打分型看各档位分布，不能全是A档

- [ ] **知识点级覆盖**：按 课程×章节×知识点 统计正例（如偏离=1）行数，**任何一次过滤后都要检查是否有知识点的正例归零**——归零的知识点在深钻里就分析不出漏报了。构建脚本应自动输出归零清单

- [ ] **章节/课程分布**：按章节统计行数，避免某章节缺席

## 第七步：构建脚本与质量检查清单

### 脚本要求

- [ ] **可重复执行，全量重建**：脚本从源文件到产出一步到位，改了规则重跑一遍即可，不做增量修补

- [ ] 校验源文件列结构，与预期不符直接报错，不静默容错

- [ ] 产出xlsx含三个sheet：**数据大表 + 质量说明 + 行数统计**。质量说明记录问题行清单和每条过滤规则的剔除行数；行数统计按课程/章节给行数、序列数、答案完整数

- [ ] 过滤有账：每剔除一行都记原因和数量，打印到控制台并写进质量说明sheet

### 数据质量检查项

- [ ] **答案完整率**：有效答案行数/总行数，缺失行单列清单

- [ ] **空值行**：关键输入字段（如对话历史、当前消息、待评输出）为空的行剔除并记数

- [ ] **轮次连续性**：序列内轮次从起始值连续递增，断档/重复/非数字的序列**整体剔除**（注意：先做来源过滤再校验连续性，AI行剔除可能造成新断档）

- [ ] **序列ID去重**：加课程-章节前缀，全表唯一

- [ ] **接力链一致**（多轮判定型）：第N轮的上轮状态输入 = 第N-1轮的期望输出；首轮状态输入为空

- [ ] **防泄漏检查**：逐字段核对判定/打分调用的输入拼装，确认答案列（期望结果/期望判断/理由）和元数据列（违规类型/数据来源等）没有混进去。这条最容易翻车，见常见坑第1条

## 常见坑清单（全部来自实战）

1. **元数据答案泄漏**：跑批拼输入时把"违规类型""数据来源：badcase构造"等元数据列一起拼进user message，等于把答案递给模型，打分虚高——输入拼装必须白名单制，只取输入列。

1. **单键分组混淆序列**：只按序列ID分组，不同章节各自的S01被混成一个序列，对话历史接力全乱——分组用章节+序列ID双键，或ID直接带前缀。

1. **AI构造行标注争议**：AI生成样本的预设答案业务方不认，争议消耗大量对齐成本——是否保留AI行先和需求方确认，我们的结论是纯生产版更可信。

1. **同类句子标注不一致噪声**：生产标注里语义几乎相同的两句话一个标0一个标1，模型怎么判都"错"一半——治理答案时按语义聚类抽查一致性，分歧行交业务裁决。

1. **ASR碎片化长对话**：语音转写把一句话切成多条短消息，轮次膨胀、单轮语义残缺——评测时按对话原样保留（生产就是这样输入的），但深钻归因时要识别这类行，别把ASR问题算成模型问题。

1. **首轮chatHistory为空属预期**：序列首轮/AI生成的首轮任务样本对话历史就是空的，这是生产真实形态，不是数据损坏——别当空值行剔除，质量说明里注明即可。

1. **拿现网系统输出当金标准的循环论证**：用被评系统自己（或同源系统）的历史输出做标准答案，测出来准确率高只说明"和自己一致"——生产系统标记只能作草稿答案，必须过业务抽检或修订（第五步）才能升级为标准答案。

## 一、客户回复（打分型 · 单轮 · 21维）

**被评对象**：模拟客户回复agent——陪练系统中扮演客户的AI，每轮HWP（健康财富规划师）发言后生成一句客户回复。

**规模**：4941条，覆盖四门课程（BAC / Pre-ATB / 健康SCC / 长寿SCC）全场景。其中BAC全场景版单文件4860条数据行、57列。

**数据源与抽取要点**：生产对话导出（陪练数据/20260615-回复/ 下 BAC 前缀文件夹）+ 课程元数据表（HWP智慧培训--课程和场景数据-BAC.xlsx 的"对练场景""对练用户"sheet）；以场景id为关联键补齐 sceneBackground（"场景背景（AI）"列）、userProfile（"对练用户"sheet 客户详情）、userPersonality（"性格（AI）"列），拼成57列大表。

**列结构实录（BAC全场景版，57列）**：

| 段                                     | 列                                                           |
| -------------------------------------- | ------------------------------------------------------------ |
| 输入列（5列，与生产agent输入一字对齐） | chatScene、sceneBackground、userProfile、userPersonality、aiTask |
| 溯源与上下文（9列）                    | 场景ID、场景实例ID、客户姓名、当前章节、当前知识点、当前任务、任务目标、历史消息、当前HWP消息 |
| 待评输出（1列）                        | 生产回复                                                     |
| 维度打分（每维2列：_分 + _理由）       | 主题相关性、话题边界守护、信息递进合理性、人设信息忠实度、回复独立语义值、关键词脱敏度、HWP跟随克制度、情绪响应匹配度、关注点克制度、专业术语回避、流程推进被动性、场景背景关联度、语气人设匹配、语句流畅自然度、口语化程度、角色立场独立性、连接词自然度、回复长度合理性，以及章节专属维度（开启面谈冷漠基线、唤起需求共情反馈） |
| 元数据（2列）                          | 数据来源、违规类型                                           |

**关键设计事实**：

- 生产agent的输入结构调研结论：chatScene、userProfile、userPersonality 固定，aiTask 始终为空，**唯一动态变量是 sceneBackground**（内容随BAC九个章节实际数据变化，从约访的简洁描述到递送保单的详细产品信息）；生产不传对话历史、不传信任度字段。评测集输入列照搬这个结构，包括保留始终为空的 aiTask。

- badcase构造覆盖6类典型违规：流程推进被动性（"你先…然后…最后…"主导流程）、HWP跟随克制度（逐点复述HWP内容）、关注点克制度（追问HWP关键词术语）、口语化程度（使用"鉴于/务必/综上"等书面词）、主题相关性（突然聊追剧/旅游等无关话题）、话题边界守护（暴露AI身份/提竞品/说精算术语）。

**踩过的坑与解法**：

1. **元数据答案泄漏**：早期跑批把"违规类型""数据来源：badcase构造"拼进了user message，badcase得分反常偏高。排查发现打分模型直接看到了答案。解法：输入拼装改白名单制，只取输入列。

1. **同一次排查还发现两个伴生问题**：英文指令（"Please score..."）搭配中文打分PE导致模型理解混乱；未强制JSON输出结构导致结果解析不稳定。解法：统一中文指令 + 强制JSON格式化输出（JSON键名一律英文）。

1. **金标准构建的路径权衡**：对无标注生产数据做人工校准集时，"AI预打分+人工复核"省时但有锚定效应，"人工盲打"可信但耗时。边界case最终由业务老师自主编写并打分，不用AI生成。

## 二、话术提示（打分型 · 单轮 · 11维）

**被评对象**：话术提示agent——每轮客户回复后，给HWP生成下一步的策略与话术建议。

**规模**：合并大表1859行、14列，覆盖四门课程；产出文件含三个sheet（合并大表 / 质量说明 / 行数统计）。

**数据源与抽取要点**：从各课程旧结构评测集（54列，含旧22维标注共44列）抽取：保留9个输入/输出列并映射重命名为PE占位符名，丢弃全部旧维度标注列，追加课程/章节/源文件名溯源列。

**列结构实录（14列）**：

```
chatScene | sceneBackground | userProfile | chatHistory | 当前客户回复 |
taskTitle | taskDesc | taskPromptDemos | aiPrompt | taskJudgeResult |
课程 | 章节 | 数据来源 | 源文件名
```

- 前9列是输入列+待评输出（aiPrompt为生产话术提示，即待评输出），列名与打分PE占位符一字对齐——源文件里的中文列名"待完成任务/任务完成要求/话术参考示例/生产话术提示"在合并时统一改名为 taskTitle/taskDesc/taskPromptDemos/aiPrompt。

- taskJudgeResult 为预留列，交付时全部留空。

- 末4列为溯源元数据：课程、章节（从文件名提取）、数据来源、源文件名。

**关键设计事实**：

- 维度体系11维，其中第11维"参考示例利用度"是双向校验：判"照搬"（字面高度相似且未融入当前对话信息）和"脱缰"（语义完全脱离参考示例核心框架），"脱缰"仅在对话阶段与参考示例适配时生效；taskPromptDemos为空时该维视为不适用（通过）。

- 合并脚本自带质量检查：关键输入字段（chatHistory / aiPrompt / taskTitle）空值行记入质量说明sheet，按课程/章节统计行数。

**踩过的坑与解法**：

1. **73行chatHistory为空引发"数据损坏"误判**：核查后确认这73行全部来源于AI生成的首轮任务样本——首轮本来就没有对话历史，属预期行为。解法：不剔除，质量说明里注明成因，避免后续接手的人再查一遍。

1. **列名不对齐的隐患**：四门课程的源文件是不同批次构建的，中文列名有差异。合并时统一映射到PE占位符名，缺列的文件打警告而不是静默填空。

## 三、任务完成判断（判定型 · 多轮多任务）

**被评对象**：任务完成判断agent——每轮HWP发言后，输出当前知识点下**所有**任务的complete=0/1状态。

**规模**：全课程大表21205行，覆盖四门课程，多轮拆行形态；产出文件三个sheet（数据大表 / 行数统计 / README）。

**数据源与抽取要点**：从"偏离评测集"目录四门课程的源文件（9列拆行形态）转换：对话历史/当前消息/知识点/任务列表照搬，答案三列留空，序列ID加"课程-章节-"前缀去重。

**列结构实录（12列）**：

```
课程 | 章节 | 对话序列ID | 知识点 | 轮次 | 对话历史 | 当前消息 |
任务列表 | 上一次任务完成情况 | 期望结果 | 理由 | 数据来源
```

- 对话序列ID格式为 课程-章节-原序列ID（如 BAC-开启面谈-D1），跨文件唯一。

- 对话历史为JSON数组字符串，消息前缀 HWP： / C：（中文冒号，生产格式）。

- **期望结果、理由、上一次任务完成情况三列交付时留空**——这是标准答案治理路线B：客户用判断agent跑一轮生成草稿答案，再由业务修订成标准答案。

**关键生产机制（评测集必须还原）**：

- **全任务同判**：每次调用输出当前知识点下所有任务的状态，不是只判一个。

- **单向锁**：任务一旦complete=1，后续轮次只能保持1，不能回退。

- **接力传递**：本轮输出 = 下一轮的"上一次任务完成情况"输入。跑批运行约定写进README sheet：按序列分组、轮次升序执行、首轮传空。

**质量过滤规则**：当前消息为空的行剔除并记数；剔除后序列内轮次不连续（断档/重复/非数字）的序列整体剔除并记数；源文件中的"期望偏离判断"列与本评测集无关，丢弃。

**踩过的坑与解法**：

1. **答案泄漏的另一种形态——PE合并**：把判定PE与打分PE合并成一个提示词，模型判定时能看到标准答案，判定准确率虚高。解法：两跳执行器物理隔离——判定跳输入不含答案，打分跳（对答案）才注入答案，指令级隔离不可靠。

1. **深钻迁就错答案**：判定与答案不一致时，深钻PE如果只许给模型找错，会强行为错答案编理由。解法：深钻PE留"疑似答案错误"出口，允许结论指向答案标错。

1. **中等边界话术的判定口径**："有内容但不够完整/生硬/模板化"的话术统一判complete=0，口径写死在构建规范里，避免同类句子标注不一致。

## 四、任务偏离（判定型 · 多轮单值）

**被评对象**：任务偏离检测agent——每轮HWP发言后，输出本轮是否偏离当前任务（0/1）。

**规模**：全课程带答案版20990行（纯生产版，AI构造行已全部剔除），偏离样本（期望=1）占比23.4%；产出文件三个sheet（数据大表 / 质量说明 / 行数统计）。

**数据源与抽取要点**：与任务完成判断同一批偏离评测集源文件；答案列（期望偏离判断）保留原值，先剔除非生产行再做轮次连续性校验，序列ID同样加"课程-章节-"前缀去重。

**列结构实录（11列）**：

```
课程 | 章节 | 对话序列ID | 知识点 | 轮次 | 对话历史 | 当前消息 |
任务列表 | 期望偏离判断 | 理由 | 数据来源
```

与任务完成判断共用同一批源数据（偏离评测集源文件9列），构建规则一致，区别在于：答案列为"期望偏离判断"（0/1单值），保留源文件原值不动；无状态接力列（偏离判定不依赖上轮输出）。

**交付结构**：评测数据、判定PE、打分PE、根因分析PE四件套，与任务完成判断完全一致；使用方法相同——环节1两跳执行器（先判定后对答案），判定跳看不到答案。

**质量治理动作实录**：

- 答案分类四档：valid0 / valid1 / 空 / 非0非1；空和非法行不悄悄剔除，列入质量说明sheet的"答案缺失/非法行清单"，行号定位到数据大表，交客户决定剔除还是补标。

- 过滤三规则按序执行并逐文件记账：① 数据来源非"生产"的行剔除；② 当前消息为空的行剔除；③ 过滤后序列内轮次不连续的序列整体剔除（AI行剔除可能制造新断档，所以连续性校验放在来源过滤之后）。

- **知识点覆盖检查**：脚本自动统计过滤前后各（课程,章节,知识点）的偏离样本行数，输出"剔除AI行后偏离样本归零的知识点"清单——这些知识点的漏报能力在深钻里无法分析，需要客户知情。

**踩过的坑与解法**：

1. **AI构造行标注争议**：AI构造行的预设答案与业务理解有分歧，逐行对齐成本高。和需求方确认后决定全部剔除，只留生产来源——这就是"纯生产版更可信"结论的出处。

1. **生产标记不等于金标准**：期望偏离判断来自生产系统标记，直接当金标准存在循环论证风险（被评系统与标记同源）。解法：答案列保留原值交付，配合质量说明的问题行清单，由业务抽检修订后再作为正式标准答案。

1. **序列ID跨章节撞号**：各章节源文件的序列ID独立编号（都从D1开始），合并大表时必须加"课程-章节-"前缀，否则按ID分组会混序列。
